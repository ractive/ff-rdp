# E3 — Manifest fetch returns HTML

## Symptoms

- "`Manifest: Line: 1, column: 1, Syntax error`."
- "PWA install prompt is missing."
- "`manifest.json` parse error in console."

## Failing layer

`<link rel="manifest" href="/manifest.webmanifest">` resolves to a URL
that responds with `text/html` instead of JSON. Common causes:

- Unauthenticated `/manifest.webmanifest` redirects to a login HTML
  page.
- SPA fallback rewrite catches `*.webmanifest` and serves
  `index.html`.
- The file simply isn't deployed; the server returns its 404 page (as
  HTML).

## Probe sequence

### 0. Ask Firefox for the parsed manifest + conformance errors (preferred, iter-104)

Instead of raw-fetching the manifest URL yourself, ask Firefox to run the
WHATWG "obtain a manifest" algorithm and hand back the parsed manifest **plus**
its conformance `errors` in one call:

```bash
ff-rdp manifest --jq '{manifest: .results.manifest, errors: .results.errors, url: .results.url}'
```

**signal → conclude:** `results.manifest` is `null` with a `reason` → the page
links no manifest (or the linked URL didn't resolve to a manifest at all).
**signal → conclude:** `results.errors` is non-empty → the manifest parsed but
is non-conformant (jump to the "Red herrings" note — this is a content bug, not
a content-type bug). **narrow → next step:** manifest is `null` but a
`<link rel="manifest">` exists → the URL is returning something that isn't a
manifest (likely HTML); confirm the content-type with step 2 below.

### 1. Find the console error

```bash
ff-rdp console \
  --filter 'Manifest|webmanifest' \
  --limit 5 --jq '.results'
```

**signal → conclude (preliminary):** syntax error mentioning the
manifest URL → suspect manifest URL identified.

### 2. Inspect the response

Preferred — Firefox does not fetch the manifest on a plain page load,
so load the manifest URL itself and capture its headers in the same
command:

```bash
ff-rdp navigate '<manifest-url>' --with-network --headers --all \
  --jq '.results.network.entries[] | {url, status,
    content_type: [.headers.response[]
      | select(.name | ascii_downcase == "content-type") | .value][0],
    location: [.headers.response[]
      | select(.name | ascii_downcase == "location") | .value][0]}'
```

`--headers` adds each entry's `headers.request`/`headers.response`
(`[{name, value}]`) to `results.network.entries`. Fetch them in the
same command that loads the page — a later `ff-rdp network --headers`
runs on a new connection and sees none of them.

This navigates the tab away from the page; `navigate` back to it before
any page-level probe.

Fallback (no `--headers`):

```bash
curl -i '<manifest-url>'
```

**signal → conclude:** response `Content-Type: text/html` (or 302 →
HTML) → **manifest URL returns HTML**. Diagnosis confirmed.

**narrow → next step:** response is `application/manifest+json` but
malformed → server-side manifest content bug; out of scope of this
playbook.

### 3. Walk the redirect chain

Each redirect hop is its own entry in the step-2 capture, in request
order; read the `status`/`location`/`content_type` triples from that
output. `curl -sIL '<manifest-url>'` prints every hop's headers.

**signal → conclude:** chain ends at `/login` → auth-gated manifest;
the manifest must be reachable unauthenticated.

**signal → conclude:** chain ends at `/index.html` → SPA fallback is
catching the request; configure the server to exempt
`*.webmanifest` (and `/manifest.json`, `/sw.js`, etc.) from the SPA
fallback rule.

## Red herrings

- `Manifest: Property '...' is required` errors → the manifest *is*
  JSON, but missing fields. Not this playbook.
- `applicationCache` deprecation warnings — unrelated.

## Worked example

Fixture: `evals/fixtures/E3/`. The fixture's `manifest.webmanifest`
file contains `<html>...</html>` content (intentionally broken).
Firefox logs a manifest parse error on load; the network response's
`Content-Type: text/html` matches the diagnosis.

## Fallback if iter-57 flags missing

`--headers` is preferred but `curl -i` is a clean alternative.
