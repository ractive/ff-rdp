## The plan

### Step 1 — Dogfood (do this first)

Run `/dogfood` against a real site with a real Firefox (153.0.4 is installed; `firefox` is
aliased to `/Applications/Firefox.app/Contents/MacOS/firefox`). Exercise **every** command and
subcommand, not a happy path.

Record, per command:
- works / broken / degraded-but-silent
- is the JSON envelope shape actually useful to a caller
- did anyone ever need it — or does it exist because an iteration added it

Deliberately probe the things recent iterations claimed to fix, since claims and reality have
diverged repeatedly (the iter-155 plan notes the stated root cause diverged from reality at least
eight times across 135–151).

**Why first:** a deep review of a codebase whose purpose is unsettled produces local nits and
burns tokens. Dogfooding produces the empirical map that scopes the review and tells a complexity
audit which code is load-bearing.

### Step 2 — Deep code review (scope it from step 1)

Multi-agent review, explicitly authorized by James on 2026-08-13. **Propose the scope and a rough
cost before spending anything** — he hit a spend limit earlier that day.

Scope by crate boundary and by what step 1 found, *not* by iteration history. Suggested lenses:
- dead / near-dead surface: `pub` items, commands, flags nobody calls
- duplicated abstraction across `ff-rdp-core` ↔ `ff-rdp-cli`
- the actor layer: how much is real protocol need vs. accreted indirection
- the discipline tooling in `crates/xtask` + `tools/` — as a **removal candidate**, not a fixture
- error/envelope machinery: is the JSON contract coherent or 155 iterations of accretion

### Step 3 — Analysis (the actual deliverable)

Write to `kb/` (its own document; link it from here). It must answer:

1. **What is ff-rdp now?** One honest paragraph, not the README's aspiration.
2. **What is it genuinely good at?** Backed by step 1 evidence.
3. **What does it do badly, or pretend to do?**
4. **What comes out?** Named files, commands, flags, crates — with the reasoning.
5. **What is the discipline machinery worth?** It has real wins (it caught the iter-151 fake-green
   ACs). It also generated four of the last six iterations. Net assessment, and a recommendation
   to keep / shrink / partially remove.
6. **What would make the next 20 iterations product work instead of process work?**

## Concrete findings already in hand (start the audit from these)

These surfaced while finishing iter-153 on 2026-08-13. They are measured, not suspected, and
they are exactly the class of thing the analysis is looking for — none of them makes a test fail,
so no gate will ever report them.

1. **`cargo test --workspace` now takes 8m21s wall for ~67s of CPU (13% utilisation).** Measured
   2026-08-13 on `main` after iter-155 merged. The cause is `test_155_skipped_live_test_is_not_-
   counted_passed` in `crates/xtask/src/live_sweep.rs`: an un-`#[ignore]`d unit test that shells
   out to a full nested `cargo test -p ff-rdp-cli --test live`. Roughly **7.5 minutes of pure
   waiting added to every workspace test run**, by a meta-test that verifies the test harness
   reports `ignored` correctly. Ask whether that verification is worth its price, and whether it
   should be `#[ignore]`-gated or moved behind `live-sweep` itself.
2. **`ac-fidelity-check`'s evidence heuristics read only an AC's *first line*.** This has now
   cost time on three consecutive iterations (154's own plan, 155's ACs, 153's AC4) — each time
   the evidence was real and in the diff, and each time the AC had to be reworded so the gate
   could see it. `unit_153_*` and `shell_154_*` match no slug regex (only `live|test|bench`), so
   an AC naming them needs a backticked symbol manually placed on line 1. This is friction the
   gate imposes on every honest author. iter-156 addresses one symptom (Theme B firing on prose);
   the first-line-only reading is the broader issue and may deserve to be folded in.
3. **Leaked processes from other projects contend for this repo's resources.** Observed a
   headless Firefox on port 6010 from a `comparis-neon` scratchpad profile plus a
   `~/.cargo/bin/ff-rdp _daemon --port 6010` respawning across observations. Not this repo's
   doing, but worth knowing when live tests behave oddly.

## Constraints and gotchas a fresh session will not know

- **Use `/new-ralph-loop`, never the old `/ralph-loop`** (it false-successes on dead panes).
- **Skill-edit iterations cannot run through the loop** — anything touching
  `~/.claude/skills/` must be hand-driven. `ac-fidelity-check.sh` has **four** copies that must
  stay byte-identical: `~/.claude/skills/{ralph-loop,new-ralph-loop}/scripts/` plus both
  `tools/` mirrors. `cargo run -p xtask -- check-discipline-regression` enforces this and must
  keep reporting `61v=FAIL, 61t=PASS`.
- **`ac-fidelity-check` cannot verify a test ran.** A green result means ticked ACs *reference*
  evidence that resolves. Live tests are `#[ignore]`-gated and never run in CI, so a ticked
  `live_*` AC needs `[verified: <YYYY-MM-DD>, <measured result>]` from an actual run.
- **`live-sweep`'s qualified path was never exercised.** Only `executed=0 skipped=219 total=219`
  (no env gates) has been verified. Launching Firefox and running live tests through it is
  untested — a good step-1 dogfood target.
- **Never `SendMessage` a workflow subagent.** It does not reach the agent; the harness forks a
  duplicate that replays implement instructions (git switches, file edits) in the *same* working
  tree. To influence a running iteration: comment on its PR (the review agent reads comments), or
  fix forward after merge.
- **kb-only changes merge locally to `main`** — no PR.
- `hyalo find --property status=planned --format text` output includes `[[wikilink]]` matches
  from document bodies; anchor with `grep -E '^"iterations/iteration'` or the list will look
  wrong (it will appear to show merged iterations as still planned).

## Open questions for the analysis

- Is ff-rdp a **CLI for humans**, a **tool surface for LLM agents**, or a **library**? The JSON
  `--jq` design implies the second; much of the ergonomics work implies the first. Nothing states
  it, and several decisions look like they were made under different assumptions.
- Is the live-test suite (219 gated tests) proportionate to the product, or is it the largest
  single source of maintenance load?
- `crates/xtask` now carries 15+ discipline checks. Which of them ever caught a real defect?
  That is answerable from git history and should be answered, not assumed.
